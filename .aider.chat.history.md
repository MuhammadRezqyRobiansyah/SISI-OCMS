This project is a Laravel-based overhaul management system for heavy-equipment components. Its main purpose is to control, document, and audit each component throughout the overhaul process at a repair or remanufacturing facility.

The system manages components such as:

- Engine
- TC/Transmission
- Final Drive
- Differential
- PTO
- Swing Machinery
- Control Valve
- Hydraulic components

Each component contains operational and identification data, including EGI model, unit code, serial number, overhaul status, SMR, lifetime, logistics information, and core category.

The overhaul workflow has seven stages:

1. Receiving
2. Disassembly, cleaning, and measurement
3. Machining and fabrication
4. Assembly
5. Performance testing
6. Painting
7. Ready for Use or Delivery

The `ComponentController` controls this workflow. It registers components, creates QR codes, starts overhaul logs, generates checksheets, validates stage completion, handles quality gates, and moves components to the next stage.

The project uses model-specific checksheets. For example, an Engine with EGI model `D375-6` receives a different checklist from an Engine with EGI model `HD785-7`. The system first searches for a template matching:

- Major category
- Stage number
- EGI model

When no model-specific template exists, it uses a generic template for that component category.

`ChecksheetTemplateSeeder.php` acts as the main checksheet master-data source. It contains:

- Receiving inspection templates for several engine models
- Receiving templates for powertrain components
- A detailed Stage 2 disassembly and measurement template for the D375-6 engine
- Generic fallback templates
- Logic for updating existing uncompleted checksheet snapshots

The system stores a copied snapshot of the template in `ComponentChecksheet`. This is important because future template changes should not silently modify checksheets that mechanics have already completed. This supports traceability and audit requirements.

The project also applies role-based workflow controls:

- Mechanic, Supervisor, and SuperAdmin can process overhaul stages
- Management approves transitions after stages 2, 3, 4, and 5
- Management can reject a transition and return the component to the current stage

There are two important automated controls.

First, the system blocks stage progression until the current checksheet reaches 100 percent completion.

Second, Stage 5 applies a performance quality gate. The oil pressure must be between 40 and 50 psi. A result outside that range stops the process.

During Stage 2, mechanics record measurement results and decide whether parts should be:

- Reused
- Repaired
- Replaced

When a part must be replaced, the system automatically creates a pending part request. This connects technical inspection results with inventory or procurement requirements.

The QR code generated during registration links directly to the component detail page. This allows personnel to access component history and current overhaul status from the physical component.

In business terms, this project is not only a checklist application. It is a digital overhaul traceability system. It combines:

- Component registration
- Inspection standardization
- Workflow control
- Approval gates
- Measurement records
- Parts replacement requests
- Mechanic activity logs
- Quality control
- Audit history
- BAST PDF reporting

A few technical risks are visible in the current implementation.

The Stage 2 inspection records may be duplicated when a mechanic submits the stage more than once before approval. The code creates new `InspectionDetail` and `PartRequest` records on every valid submission without checking whether the same result already exists.

The `ensureChecksheetForStage()` method stops when any checksheet already exists. It does not repair an existing empty or incomplete snapshot when the template changes.

Template selection relies on `UPPER(egi_model)` and normalized user input. It handles letter casing, but inconsistent spaces or alternative model naming can still cause a generic template to be selected unexpectedly.

The seeder contains a large amount of operational master data in one PHP file. It works, but long-term maintenance will become difficult because checklist content, migration behavior, and snapshot-repair logic are mixed together.

Overall, the project is designed to digitize the complete overhaul lifecycle of heavy-equipment components while maintaining process discipline, management approval, technical evidence, and historical traceability.
